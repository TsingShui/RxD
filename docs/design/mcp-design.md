# MCP service

Status: implementation contract.

The local entry point is `rxd mcp serve`, built with Cargo feature `mcp`. See
[ADR 0007](../adr/0007-typed-mcp-service.md) and
[ADR 0003](../adr/0003-output-envelope.md); runnable examples are in the
[MCP demo](../demo/mcp.md).

## User-level registration

Registration, preview, repeated setup and standalone MCP startup/discovery/target
lifecycle are non-backend operations with no 150 ms acceptance requirement. Real
functional/safety/lifecycle checks and finite resource limits remain required. Backend
analysis invoked over MCP keeps its existing query/worker performance contracts.

`rxd mcp install [-a pi|cc|codex|all] [--preview] [--replace]` registers the executable
without starting clients, workers or native engines. Repeat `-a`; `claude` and
`claude-code` alias `cc`. Selection is de-duplicated in pi/cc/codex order. No selection
detects only a resolved native config file/directory or an executable on PATH; when
nothing is detected it fails rather than inventing a skills destination. Explicit
selection can create a client configuration. MCP-disabled builds have no installer.

Pi writes `$PI_CODING_AGENT_DIR/mcp.json` (default `~/.pi/agent/mcp.json`); empty
overrides are unset and leading `~/` expands against HOME. CC writes `~/.claude.json`,
or `$CLAUDE_CONFIG_DIR/.claude.json`. Native CC 2.1.301 gives
`~/.claude/.config.json` / `$CLAUDE_CONFIG_DIR/.config.json` precedence when present;
invalid legacy configuration fails without fallback. Codex writes
`$CODEX_HOME/config.toml` (default `~/.codex/config.toml`). Pi/CC use JSON
`mcpServers.rxd`; Codex uses TOML `mcp_servers.rxd` and preserves comments. A client
configuration directory override alone is not detection evidence. CC's default
detection directory is `~/.claude`, not HOME.

The command persists absolute executable/base/root argv starting `mcp serve`. Initially
the base and sole allowed root are the installation cwd; an implicit root equal to or
containing HOME, or a filesystem/volume root, is refused, including with `--base` alone.
Use explicit `--root` for the intended analysis directory; explicit and recognized prior
explicit roots retain serve semantics. Implicit roots use macOS `statfs` mount paths,
Linux `/proc/self/mountinfo` in the process namespace (4 MiB bounded read, decoded
mount paths including same-device bind mounts), or Windows `GetVolumePathNameW`
(bounded 32,768-unit path buffers). No configured programs or external mount commands
are executed. Device-parent heuristics alone are insufficient, including APFS firmlinks.
Mount identity errors refuse implicit authority with explicit-root guidance; other
platforms require explicit roots when native mount identity is unavailable.

`--base`, repeated `--root` (relative to base) and comma-separated `--backends` use the
server's existing path/catalog semantics. Recognized updates keep prior roots/base/
filter unless explicitly selected; no-op repeats leave bytes untouched. Recognition
requires valid `mcp serve` argv, stdio/no URL, and either the exact current executable or
a basename exactly `rxd`/`rxd.exe` (not `rxd.sh`, `rxd.py` or `rxd.wrapper`). This is a
bounded convention, not provenance proof. A relocated custom executable name is
ambiguous: use `--replace` explicitly. Replacement changes startup fields, not other
servers, credentials or entry controls such as enabled, env, timeout and exposure.
Replacing a conflict establishes fresh launch defaults.

Stdout is one JSON object `{preview, targets}` with deterministic target order and
agent/path/outcome/registration fields. Outcomes: installed, updated, unchanged,
conflict, failed, not-written (aborted preflight). Preview reports intended outcomes
without creating files/directories; registration includes only managed launch fields,
never unrelated config/credentials. Diagnostics and reload guidance go to stderr.

Input and final generated configurations are bounded at 4 MiB; malformed/duplicate-key
JSON, malformed TOML, wrong shapes, symlink/special config files and known unwritable
targets fail safely. Oversized generated bytes reject the complete plan, including
preview, before any staging or directory creation; unknown values are never truncated
and the reader bound is never raised. Outcomes are typed internally and serialized only
at the reporting boundary. All selected configs are parsed before staging; all changed
files are staged before replacement. Existing permissions are retained. Each replacement
rechecks bytes, file identity/metadata and parent resolution for concurrent changes; this
is not a cross-client transaction. A late publication failure reports each actual
outcome and returns failure; earlier successful replacements are not rolled back.

Persisted configuration is not a verified live session. The conservative Pi session
verification floor is 1.3.0; this does not claim all earlier releases are incompatible.
Pi settings disabling `builtin:mcp` or MCP-named extensions produce bounded warning
codes when detectable; arbitrary extension hooks cannot be proven statically. An
extension registering `/mcp` replaces native session MCP even when shell listing
connects. Disabled entries, hidden exposure and tool filters are retained, never enabled
by registration. Reload Pi with `/reload` and inspect `/mcp`; restart CC/Codex and
inspect their MCP state. Trusted project settings, profiles and managed policy can
override user registration. No trust, credentials, approval, enablement or policy is
changed. Full paths, precedence, compatibility and manual fallback are in the
[onboarding guide](../demo/install.md#agent-onboarding).

### Native-client verification boundary

The optional native-client verifier (`scripts/verify-mcp-clients.py`) requires explicit
existing executables and fails when a requested client is unavailable. Ordinary offline
Rust tests do not require client applications. The verifier relocates the release binary
to a space/Unicode path, installs into isolated native configs with no inherited provider
credentials, launches from a different cwd, queries a known JS literal through relative
base resolution and rejects an outside-root query. Recorded commands come from native
JSON or actual Codex readback, not installer stdout. Engines stay lazy.

The verifier covers Pi shell discovery and actual SDK session-wrapped codemode tool use;
Claude Code generated-config `get/list` plus a separate recorded-argv MCP query/denial;
and Codex `get/list` plus an app-server no-turn thread/status/tool-call query/denial.
Pi imports a schema-valid deterministic assistant toolCall through the public in-memory
SessionManager/refreshContext, satisfying the session's assistant-history precondition
without a model/provider stream. Native nested validation, tool_call/tool_result hooks
and correlated parentToolCallId events are asserted. Disabled-built-in, replacing `/mcp`
extension and disabled-server fixtures show configuration is not session use. This is
not model-issued Pi use, a CC session invocation, or evidence for a real user's
overridden session. No prompt/turn-start inference, trust/policy changes or application
installation occurs. Codex uses an isolated loopback-only provider, not hosted auth.
Version/hash/config/protocol logs are external evidence, not embedded product inputs.

Fresh-process measurements are not acceptance gates. Client startup, models, network
and engine provisioning are outside the measured command; timings cover complete
startup, output and writes for install/preview/update workloads. Results are reported
with conditions and retained failures; no universal latency or cross-client transaction
claim follows.

## Transport and discovery

rmcp is pinned to 3.5.1 with stdio/server dependencies only. The legacy lifecycle is
`initialize` → `notifications/initialized` → discovery/calls. The modern 2026-07-28
lifecycle supports `server/discover` and per-request client/version metadata; request
`_meta` must contain `io.modelcontextprotocol/protocolVersion`,
`io.modelcontextprotocol/clientInfo` and `io.modelcontextprotocol/clientCapabilities`.
Protocol-version negotiation and rejection follow the pinned SDK and wire tests. Close
stdin to end the local session; there is no custom shutdown tool.

Only MCP traffic enters stdout. Each bounded frame is one complete JSON-RPC line.
Malformed input and frame overflow are explicit protocol failures, never analysis
success. `tools/list` exposes closed `inputSchema` and `outputSchema`, backend/capability
`_meta`, and descriptions retaining inference, fallback, IDs and engine-availability
constraints. Catalog filtering uses CLI namespaces (`jar`, not `jvm`). Disabled tools
cannot be called. Startup and catalog discovery do not load ILSpy or unpack Kuna specs.

**The CLI is the single contract source.** A tool is exactly one analysis command:
`<backend>_<command>`, and its schema and argv are reflected from the `clap` tree at
runtime (`src/query/reflect.rs`), so a renamed or added flag cannot leave one surface
behind. The names are the shared CLI vocabulary: `entities`, `functions`, `classes`,
`methods`, `fields`, `entries`, `types`, `codes`, `blocks`, `interface`. Only three
things are MCP-specific: the path positional becomes `input` (`inputs` for `--apk` list
commands), `-o/--output` becomes the artifact channel, and `--perf` is
hidden. Every other flag appears verbatim with its help text as the property
description: a row selector is `at`, a substring filter is `filter`, original bytes are
`raw`, `dotnet_xref` takes `at`/`from`/`string`, and `dex_xref`/`jar_xref` take `kind`
plus that kind's own arguments. Naming is the flag spelling, never a second vocabulary.

No backend exposes a `--max-*` ceiling any more, so no ceiling reaches a worker as a
flag. MCP explicitly selects the fixed `rxd_core::Budget::default()` policy, not the
ordinary CLI's input-scaled policy (ADR 0016), and the server's only per-call
knob is the thread budget. A command that declares `--threads` is given
`min(requested, max-threads / worker-slots)`, so a caller may ask for fewer threads,
never for more. Request-level budgets stay where the protocol already has them: the
captured output is capped at one quarter of `max-response-bytes`, the record sink is
capped at the shared record ceiling, and the complete RPC frame is checked against
`max-response-bytes`.

| Backend | Analysis tools |
| --- | --- |
| js | entities, functions, classes, methods, find, identifiers, calls, members, locate, xref, symbols, get |
| asar | entries, extract |
| html | entries, extract |
| dex | get_class, entries, strings, xref, manifest, classes, get_method, fields, methods |
| jar | classes, entries, fields, methods, get_method, get_class, strings, xref |
| dotnet | classes, fields, methods, get_method, get_class, strings, xref |
| wasm | types, imports, exports, functions, tables, memories, globals, data, elements, strings, xref, get_function |
| pyc | codes, strings, xref, get_code, decompile |
| evm | analyze, interface, storage, disassemble, basic_blocks, cfg, metadata, blocks, strings, xref, get_block, get_function |
| kuna (bundled-kuna only) | functions, decompile |

There are 69 built-in analysis tools plus `rxd_open`/`rxd_close`; linked Kuna adds only
the two listed tools. DEX keeps descriptor/entry/index selection and null entity IDs.
EVM projects inferred analysis and accepted static navigation/reconstruction contracts;
unknown discovery, ownership and unsupported reconstruction remain explicit. Native
Kuna JSON keeps its own typed format and per-function error fields.
`kuna_decompile` takes exactly one `name` or hex-string `address`; use a returned
`functions[].address_hex` as `address` to preserve 64-bit precision. Names cannot contain
commas, NUL, surrounding whitespace, a leading `-` or native `0x` address syntax.
Ambiguous names return `AMBIGUOUS` with complete typed native candidates. Enumeration is
full, not an implicit summary. Effective per-function instructions are bounded by the
lower of request/server and native 100,000 ceiling; truncated native source is an explicit
failure. Engine version/revision/limited adapter coverage are declared in catalog
descriptions; producer JSON is unchanged. The isolated MCP entry forces one native
decode lane even when `KUNA_DECODE_JOBS` is inherited; the ordinary Kuna CLI keeps its
own environment policy.

## Inputs, identity and lifetime

Normal tools take `input: {path: "..."}` or `input: {target_id: "..."}`, exclusively.
Relative paths resolve against `--base`, defaulting to the server startup cwd. Repeated
`--root` entries authorize local roots; omission authorizes only the base. Opened
handles are validated against roots with no-follow/special-file refusal. This is a local
file access policy, not an OS sandbox or authenticated remote interface.

`rxd_open` takes exactly one `path` or nonempty `paths`; optional `backend` establishes
capture scope. Use `backend: "js"` for directory discovery, `"asar"` for complete
unpacked dependency capture, and `"dex"` for an ordered multi-input bundle. Other
backends capture a regular file. File bytes are copied into private managed storage, not
merely held in mutable mmap/open-file handles. No analyzed input is executed.

The result has `target_id, source_id, snapshot_id, input_bytes, captured_bytes, kind,
inputs, origin`. Each input reports its logical original path, relative path where
applicable, original byte SHA-256 and size, and dependency flag. `source_id` identifies
primary content; `snapshot_id` additionally identifies the captured file/dependency/
bundle set. Neither replaces backend unit IDs (JVM class hash, .NET token, PYC tree index,
etc.). Handles belong to one server process, expire after a fixed TTL from publication,
and are never reopened implicitly. `rxd_close` returns `{target_id, closed: true}`.
Unknown, closed, expired or previous-process handles return `TARGET_INVALID`. Already
acquired calls retain their copies and quota until completion/reaping.

One-shot path calls allocate transient captures and no durable target slot. JS directory
capture selects the same extensions as the CLI, preserves file-set boundaries and rejects
links/special children. Discovery entry count, files, bytes and depth are independently
bounded. Windows DOS device names, alternate streams, control/invalid characters and
trailing dots/spaces are explicitly unsupported for physical snapshot names; accepted
logical labels are preserved. `--max-snapshot-depth` accepts 1–256, default 64.

Every DEX tool requires one captured file; a bundle passed to a single-input operation
fails.

HTML `html_entries` captures one regular immutable file for a path or file target. Its
`lexical_naive_v1` records are not a DOM or browser-complete parse; no page code executes
and no external resources load. Header/records/summary retain CLI values and order with
logical paths restored (not byte-identical JSONL). Filters `kind/tag/attr/within/depth/
filter` are the CLI flags of the same name; records carry their `at` coordinate and the
reporting node in `context_at`. `html_extract` reuses backend validation, selection,
receipt and artifact identity: its `at` argument is the coordinate an `entries` row
prints, and it returns the CLI receipt with `detail.path: null` plus `child_target`;
`include_bytes: true` adds `bytes_base64` and omission avoids the copy. The child owns the
exact selected bytes independently of parent close; target-origin retains
container/node/range and the parent handle where available. There is no host output
destination argument.

ASAR open/extract captures only declared unpacked dependencies under roots; missing/
linked/size-mismatching dependencies fail explicitly. Direct `asar_entries` captures archive
metadata and does not require unrelated unpacked files to be readable. Existing archive
links remain listable but cannot be followed; each file row prints its archive-relative
path as `at`. `asar_extract` takes that same `at` and returns the CLI receipt with
`detail.path: null` plus `child_target`; the child owns its bytes independently, and
origin identifies archive/entry and parent handle where available. `include_bytes: true`
adds `bytes_base64`; omission avoids the copy. There is no host output destination.
Content/format checks, not entry extension, select the next backend.

## Structured results and errors

Results are shaped generically from the captured stream, with no per-tool mapping:
ordinary JSONL becomes `{header, records, summary}`, recursive JS becomes
`{files: [{header, records, summary}], scan_summary}` including zero-file scans (an
empty scan is `{files: [], scan_summary}`), a single JSON object is returned unchanged
(a FETCH record or a whole-class document), and any other output (XML manifest, Java or
C# source, original text) is returned as `{text: "..."}`. Stable outer navigation fields
remain nullable under schema version 2: `at` names a record, `parent_at` its structural
owner and `context_at` the caller that reported it, so no caller depends on a
backend-specific identity key. Original text is unchanged, including line endings. JS get
uses its native source record (`detail.source`); instruction/C#/PYC results retain native
fallback/completeness. JS isolated UTF-16 surrogate values project as
`{utf16_units: [integer, ...]}`; ordinary values remain strings. These code units preserve
the original value without replacement.

Each result appears in `structuredContent` and as one JSON text compatibility block.
Consumers check `isError` before interpreting success. Domain failure has
`{error: {code, message, candidates}}`; `candidates` is nullable and carries the complete
typed result when the surface has one, so no caller parses diagnostics. A coordinate that
no longer names a row is `NOT_FOUND`, exactly as on the CLI (ADR 0015); `INVALID_QUERY`,
input/identity errors, `RESOURCE_LIMIT`, `TARGET_INVALID`, `TIMEOUT` and `WORKER_ERROR`
guide recovery. Protocol faults are
JSON-RPC errors. Cancellation suppresses responses as required by the SDK;
completion/cancellation races follow the negotiated protocol.

Success means complete delivery of the selected query, including explicit filters. It
never means successful source reconstruction unless native fields say so.
Budget failure returns an error, not success with a shortened record list or text.

## Scheduling and finite defaults

All analysis runs in isolated disposable workers, including DEX and optional Kuna. Target
capture is bounded and cancellation/deadline checked; parser/decompiler state is not
cached across workers. Fixed input hashes may be reused once the snapshot invariant is
established. ILSpy/Kuna initialize only when the selected worker needs them.

| Startup option | Default | Meaning |
| --- | ---: | --- |
| max-frame-bytes | 1,048,576 | Incoming frame including newline |
| max-response-bytes | 33,554,432 | Complete RPC response and compatibility copy |
| max-active-requests | 16 | Retained protocol requests, including admission replies |
| max-workers | 2 | Analysis slots; further limited by max-threads |
| max-threads | 4 | Total analysis threads across worker slots |
| deadline-ms | 30,000 | Capture plus analysis deadline per call |
| max-worker-bytes | 67,108,864 | Each worker request/result IPC bound |
| max-native-worker-bytes | 268,435,456 | Sampled RSS ceiling per linked Kuna worker; startup can only lower |
| max-targets | 64 | Durable handles |
| max-live-captures | 128 | Durable/transient/acquired captures |
| max-snapshot-bytes | 1,073,741,824 | Aggregate retained stored bytes |
| max-capture-bytes | 268,435,456 | Per capture stored bytes |
| max-snapshot-files | 10,000 | Files in one capture |
| max-snapshot-entries | 100,000 | Discovered directory entries |
| max-snapshot-depth | 64 | Directory/dependency path depth; safe ceiling 256 |
| target-ttl-ms | 600,000 | Fixed handle retention |

Worker slots are `min(max-workers, max-threads)`; each gets floor(max-threads/slots)
analysis threads. Excess admission fails immediately with `RESOURCE_LIMIT`. Close/
lifecycle traffic stays usable; there is no unbounded waiting queue. Output backpressure
and correlation IDs are part of transport accounting. Worker request/results and stderr
are bounded, concurrently drained, and workers are stopped/reaped on cancel, timeout or
EOF. A failed worker does not stop the protocol service or unrelated admitted work.

A CLI-projected tool has no per-call `limits` argument: a backend ceiling has no CLI
flag, so a tool argument cannot carry one either. Only the typed native Kuna adapter
keeps its own native `limits`, because those are its own protocol fields, not CLI flags.
The CLI projection explicitly preserves `rxd_core::Budget::default()` (8 GiB input
subject to format spans, one-million work/semantic nodes, 100,000 instructions,
128 MiB metadata/output, AST depth 512). Protocol snapshot/record admission remains
independent and can be tighter. ADR 0016's ordinary CLI scaling does not apply here: the captured serialized output
is capped at one quarter of the response ceiling (default 8 MiB) - a transport bound the
protocol owns, not an analysis budget - and the complete RPC frame at
`max-response-bytes`. A
result that exceeds any of those fails with `RESOURCE_LIMIT`; it is never shortened. The
final complete-RPC size check includes JSON escaping, base64, provenance, compatibility
copy and correlation metadata; a result may still fail it. Backend-native lower caps
continue to apply where the adapter preserves them.

Linked Kuna workers also have an owned-process RSS guard sampled nominally every 5 ms on
the existing async supervisor. `--max-native-worker-bytes` accepts 1–268,435,456 bytes;
the 256 MiB default is also the maximum. Observed excess stops/reaps that worker and
returns `RESOURCE_LIMIT`; this is a sampled guard, not an instantaneous kernel cap. It
applies only to native Kuna analysis workers, not ordinary JS workers. These are bounded
accounting contracts, not hard total RSS limits across the service and all engines.

## Verification and future transport

The verification seam is a real stdio client → actual binary. Offline fixtures,
independent parsers/bytes and CLI parity cover every catalog operation and returned-ID
workflow, roots, snapshots, DEX ambiguity, fallback, corruption, cancellation, EOF and
worker failure. Benchmarks separate first-use/open/reuse/workflow/concurrency/RSS,
preserve failures and actual complete writes. Fresh Agent measurements include full
`tools/list` typed capability discovery and routing; full fresh navigation additionally
includes required open and close. Initialization/query subtotals alone are not full
fresh-session evidence. CLI latency requirements remain unchanged; long-lived query
measurements cannot replace fresh CLI acceptance.

Streamable HTTP/HTTPS is a future transport around the same typed service/query boundary.
TLS, authentication, authorization, uploads, caller isolation and remote retention are
outside this release and require separate design. This entry point exposes no network
listener.

EVM navigation uses the current CLI's fixed nullable stream fields and carrier/encoding
bound coordinates: `evm_interface` lists content-bound function candidates,
`evm_blocks` lists content-bound basic blocks, and `evm_get_block`/`evm_get_function`/
`evm_xref` take the `at` a row prints. `evm_strings` accepts explicit text/bytes/number
interpretations; `evm_xref` preserves PUSH-use, CODECOPY and code-flow evidence;
`evm_get_function` requires exactly one `at` or `selector` and keeps raw/default
reconstruction and structuring facts. Native defaults remain ceilings through
`rxd_core::Budget`, including 4 MiB carrier input; no navigation budget can be lowered
per call.
