# JAR product benchmark

Compare the latest GitHub releases of JADX, CFR and **Jar Analyzer Engine** with a
frozen local release rxd binary. This uses the official headless engine CLI, not
the Jar Analyzer GUI. `bench.py` resolves versions afresh, verifies available
GitHub asset digests, and records exact artifact hashes and versions in its report.

```sh
CARGO_BUILD_JOBS=2 cargo build --release --no-default-features --features backend-jvm
python3 benchmarks/jar/bench.py --binary target/release/rxd --samples 10
```

Tools, logs, source outputs and reports stay under ignored `target/benchmarks/jar/`.
Open `target/benchmarks/jar/engine-run/index.html` for the chart, or read its sibling
`comparison.svg` and `result.json`. Requires Python 3.11+, Java/JDK (including
javap), and authenticated gh. No GUI is launched, and analyzed input is never executed.

## Inputs and scope

- Gson 2.11.0 / JsonPrimitive (repository corpus).
- Rhino 1.7.15 / ClassShutter (repository corpus; deliberately includes an interface).
- Hadoop Client Runtime 3.4.1 / shaded commons-lang3 CharUtils (large single JAR).

Download the Hadoop input to the expected ignored location before running:

```sh
mkdir -p target/benchmarks/jar/inputs
curl -fL https://repo.maven.apache.org/maven2/org/apache/hadoop/hadoop-client-runtime/3.4.1/hadoop-client-runtime-3.4.1.jar \
  -o target/benchmarks/jar/inputs/hadoop-client-runtime-3.4.1.jar
```

Expected Hadoop SHA-256:
`f6a800a159f918670db533606d33560d6c13b7e13f14eda493280ae33b9eeb2f`.
The runner verifies pinned input hashes and records sizes, class counts and
selected-class sizes. These are selected-class tasks, not whole-JAR reconstruction
or a complete comparison of every rxd query. Other operations still need their
own adapters; missing adapters do not mean a competitor lacks the capability.

## Timing boundary

Every sample starts a fresh CLI process and measures through process exit and
complete output collection, including startup, input reading, reconstruction and
file/pipe writes. For Jar Analyzer Engine, each sample uses an empty working
directory and invokes its stock CLI:

```sh
java -XX:ActiveProcessorCount=2 -Xmx2g -jar jar-analyzer-engine-1.2.0.jar \
  --jar library.jar --decompile com.example.MyClass --log-level ERROR
```

Automatic database construction and class extraction are inside that measured
process; no index, extracted-class directory or source cache is reused. This is
an end-to-end product task: the engine may do more preprocessing than its peers.
It is not an isolated decompiler-engine throughput measurement.

Filesystem caches are not flushed, and no warm-up samples are discarded. Java
processes use `-XX:ActiveProcessorCount=2 -Xmx2g`; JADX uses two processing threads.
Raw samples, first-sample time, median, P95, maximum and failures remain in JSON.
First-sample executable validation/startup outliers are retained. The runner
freezes and hashes the rxd binary before measuring, and saves a representative
source/log artifact for each input/tool; subsequent sample output directories
are removed after verification to avoid duplicate caches.

Older `run*`/`cold-run` results used the GUI product and may include confirmation
waits or resident cached queries. Those results are invalid for this comparison;
only `engine-run` reports generated by the current runner apply.

## Correctness and interpretation

Validate one selected source file/class and declared method names against an
independent javap inventory before treating a sample as successful. This is not
proof of overload completeness, body correctness or semantic equivalence. Generated
source quality must be reviewed independently; no fastest-tool claim follows from
latency alone. Validation failures stay in JSON and appear as failures in the
chart, never as fast successful results. Earlier frozen rxd builds failed the
Rhino interface case because their output omitted `interface`. The corrected
build must pass the same validation; old results must not be relabelled as fixed.
